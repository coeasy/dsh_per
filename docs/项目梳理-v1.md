## 1. 项目定位

**dsh-per 是 DSH（Cordis 宿主）上的多模型编排插件**：把一个大任务拆成「规划 → 执行 → 复核」三阶段流水线，每阶段绑定不同模型，并内置自动修复回路、预算护栏与降级链。

一句话概括架构：**数据驱动的 FSM 迁移表是唯一的控制中枢**，其余模块（协议解析、路由、预算、机械验证、持久化）都是被 FSM 的 hook 调用或向 FSM 喂事件的**无状态服务**。

插件形态：
- 普通 Cordis 插件，`package.json` 的 `dsh.bundle.patch` 指向 `cordis.patch.yml`，被 profile 依赖后自动加入层栈。
- bundle 默认插入的 `orchestrator` 行配置为 `{}` → **无 stages 即惰性**（ADR #13：`mode=auto` 且无阶段模型一律 passthrough）。
- 宿主接口只有一个对象 `ctx`，插件通过 `ctx.on / ctx.get / ctx.inject / ctx.effect` 接线，**没有任何 Service class**，避免 profile 内跨实例的 class identity 问题（`plugin.ts` 用 apply 风格）。

### 3.1 两条正交的「驱动轴」

插件的运行不是一条调用链，而是**两条轴在同一个 FSM 上交汇**：

| 轴 | 输入 | 处理 | 输出 |
| --- | --- | --- | --- |
| **推轴**（turn 驱动） | `agent/turn-stopping`（每回合结束） | `onTurnStopping` 按 `task.state` 做 switch，决定发 `steer` 指令还是发事件 | 下一回合的定向指令（`pendingSteer`） |
| **拉轴**（事件驱动） | `session/event`（assistant/message、tool/result、step/end、turn/start） | `onSessionEvent` 记账、检测计划围栏、采集 diff、捕获 `[NEED_REPLAN]` | 事件（`transitionOrLog`） |

两条轴**唯一**的汇合点是 `task.transition(event)`。这正是本项目的核心设计约束：**引擎的任何地方都不直接改 `snapshot.state`**，只能通过 `transition()`（`engine.ts:402`）或 `forceAbort()`。

### 3.2 配置五层解析（v5.3）

`engine.ts:126` 的注释给出权威顺序（高 → 低）：

```
会话 /orch set        ← sessionOverrides: Map<sessionId, {plan|execute|review: model}>
  > settings 用户段    ← settings.yaml 的 dsh-per 键（UI 保存落地处）
  > saved-overrides.json（/orch save）
  > 插件补丁 config     ← cordis.patch.yml 的 orchestrator 行（整体替换，不合并）
  > schema 默认        ← config/schema.ts 的 zod .default()
```

实现要点：
- `effectiveConfig` **只包含全局层**；会话级 override 在绑定时通过 `sessionEffective(sessionId)` / `router.resolve(…, { override })` 逐会话应用，绝不合并进全局（多会话宿主不能让一个会话的 override 泄漏到另一个）。
- settings 段读取的是**原始用户层**而非 seam 解析值（`engine.ts:161` S2 注释）：因为 `scope.get()` 会把 schema 默认 + 注册 base + 用户层混在一起，喂给 overlay 会掩盖 saved-overrides。`describe()` 暴露原始用户层，每次 watch 重读。
- settings 注册失败（schema 拒绝、provider 竞态）→ 降级为「仅补丁配置」，不拖垮插件（D11）。

## 5. 关键机制实现细节

### 5.1 FSM 与迁移表（控制中枢）

**表结构**（`transition-table.ts`）：`Partial<Record<TaskState, Record<rowKey, TransitionRule>>>`，其中 `rowKey` 可以是精确事件名，也可以是 `${event}:${variant}` 复合行。`TransitionRule = { to, guard?, fallback?, action? }`。

**`action` 是声明式的**，`fsm.ts:212 applyAction()` 按字面操作符解释：
- 计数器：`plan_retry++` `exec_retry=0` `replan_cycle++` `fix_cycle=0` `review_supplement=0` `review_dispatch_retry=0` 等 12 种。
- 步数预算复位：`plan_steps=0`、`execute_steps=0`（防止跨轮累计误触发 steps-exceeded）。
- 语义标记：`planVersionBump`、`replacePendingFixes`（从最新 verdict 取非 minor 问题）、`recordStreaks`（issue 稳定 id 跨轮追踪，消失即清零 = M5 契约）、`synthesizePlanDefectIssue`（合成 `SYN-PLAN-DEFECT` blocker）、`clearFixEscalated`、`planningReturnState`。

**`transition()` 行解析算法**（`fsm.ts:125`）：

```
1. 终态 → return false（无出边）
2. event == 'plan/retry' → 取 PLAN_FAIL 的同名行并改写 to = planningReturnState（A2）
   否则 GLOBAL_EVENTS[event] → 作为首个候选（任何非终态都可被打断）
3. 过滤出 k === event 或 k.startsWith(event + ':') 的行
   排序：精确行排最前（(a===event ? -1 : 0) - (b===event ? -1 : 0)）
4. 顺序扫描候选：首个 guard 通过（或无 guard）即中；记录最后一个失败的 fallback
5. 无命中：有 fallback → 递归 transition(fallback, depth+1)；depth > 2 → forceAbort('guard_chain_overflow')
   无 fallback → illegalTransitions++ → forceAbort('guard_rejected')
6. 写 state → applyAction（同步、原子）→ updatedAt → enqueue(hook)
```

**两条要注意的细节**：
- **hook 串行化但 state 变更不是**：`enqueue()` 只串行化 hook 执行（`fsm.ts:113`），`snapshot.state = chosen.to` 与 `applyAction()` 在 `transition()` 主体内同步完成。引擎存在多个异步入口指向同一 task（`session/event`、`turn-stopping`、`request-error`），理论上可并发进入同一 task 的 `transition()`。
- **复合事件由引擎显式指名**：`engine.ts:1105` 发的是 `'exec/ok:DONE'` 而不是 `'exec/ok'`，`review/pass:MISS` 则靠守卫选择（精确行 `review/pass` 带守卫 `!mechanicalFailedAfterPass`）。也就是说**「无守卫的精确行会屏蔽后面的变体行」**这条规则对 `exec/ok` 起作用，但引擎绕开了它——见方案文档 §P1-07。

**状态迁移全景**：

```
                       ┌────────── task/launch（guard: configValid && budgetOk）
                       ▼
                       IDLE ──┐
                              │（launch 失败 → guard_rejected → ABORTED）
                              ▼
                     ┌───── PLANNING ◄──────┐        replan/fail:EXHAUSTED
                     │  ▲        │          │                        │
        plan/retry ──┘  │   plan/ok (schema ok)│         RE-PLANNING ◄┤
        plan/steps-     │  │                 │       ▲   │           │
          exceeded      │  │                 ▼       │   │           │
                     PLAN_FAIL           EXECUTING ──┼───┴──┬────────┤
                     (plan_retry++)    ▲  │  │  exec/need-replan      │
                                      │  │  └─exec/fail → (exec_retry)│
                                      │  │      └耗尽→exec/fail:REPLAN┤
                                      │  └─exec/steps-exceeded ──────┤

### 5.2 三阶段协议

**规划（fenced 协议，ADR #26）**
- 引擎在 `systemPrompt.section('orchestrator:stage')` 注入阶段指令；规划阶段要求模型输出**单个** ```` ```plan ```` 围栏 JSON。
- `onSessionEvent` 在 `assistant/message` 上正则 `/```plan\s*\n([\s\S]*?)```/g` 取**最后一个**围栏块 → `parsePlan()`（`protocols/plan.ts:51`）：`JSON.parse` → zod `planDocumentSchema` → 返回 `{ ok, plan, auditResponse }`。
- **`version` 由 FSM 分配**（`attachPlan` 里 `version: planVersion + 1`），模型输出的 version 被忽略；`audit_response` 单独透出，**不进入持久化计划文档**。
- 失败路径把 zod 的 `path:message` 拼接串作为 `lastPlanError` 回注下一次重试指令。
- `estimateTokens` = `ceil(chars/4)` 粗估；超过 `estimated_context_tokens * 0.8` 置 `planDigested = true`，后续规划/重规划指令要求「精简版计划」。

**执行**
- 计划全文通过 system prompt 注入（`EXECUTING` 分支），加上 `pendingFixes` 与 `userDirectives`。
- 执行侧信号：`tool/result` 的 `error` 累加 `execErrorCount`（子代理错误被过滤），`meta.diff`/`meta.diffLines` 累加 `diffLines`；`execErrorCount` 在 `turn/start` 每回合清零。
- `[NEED_REPLAN]` 文本标记 → `snapshot.needReplan = true` → turn 边界触发 `exec/need-replan`。

**复核（ADR #17：独立子代理 + outputSchema 强制）**
- `dispatchReviewer`（`engine.ts:730`）经 `subagents.start('spawn', { parent, prompt, signal, agentOptions: { provider, model }, outputSchema: reviewVerdictJsonSchema() })` 派发。
- **provider 必须显式解析**：子代理无法通过请求瀑布继承 provider，解析顺序为 review 路由覆盖 → 父会话实时路由 → `agentDefaultModel.currentSelection()`。
- **单定时器**：`review_dispatch_timeout_ms`（默认 300000）超时即 `run.dispose()` 并让 race 解析为 null → 转死锁；finally 清定时器，避免已完成 run 残留 5min 定时器把 headless 进程挂住。
- verdict 走 `reviewVerdictSchema.safeParse`（harness 只强制受限子集，区间校验交还 zod）→ 推入 `reviewHistory` → 清 `lastReviewError` → 重置 `review_dispatch_retry`。
- 死锁语义（A2）：每轮一次重派预算；耗尽则**保守合成** `SYN-REVIEW-DEADLOCK`（major/execution/confidence 0.7）并转 `review/deadlock:EXEC`，走正常 fix loop，全程有界。

**verdict 路由（`routeVerdict`，纯机械规则，编排器不做语义判断）**
| 条件 | 路由 |
| --- | --- |
| `pass === true` | `review/pass`（若机械验证 fail → 引擎置 `mechanicalFailedAfterPass` → 走 `review/pass:MISS`） |
| `confidence < 0.7` 或 `defect_type === 'ambiguous'` | `review/ambiguous` |
| `defect_type === 'plan'` | `review/fail-plan` |
| 其余 | `review/fail-exec` |

`review/ambiguous` 最多一次补证（`review_supplement` 守卫 `< 1`）；补证后仍不明确 → 保守按执行缺陷处理。**补证预算每轮重置**（E2E 第 4–6 轮统一了 ok-失败路径与 deadlock 路径的分叉）。

**机械验证（A11）**
- `spawn(command, { shell: true, cwd, windowsHide })`，`compile` 与 `tests` 顺序执行；`timeout_ms` 超时 `SIGKILL` → `unavailable`。
- 输出收集上限 100KB（截断保留末 50KB），`tail` 取末 2000 字符，`summarizeTests` 用 4 组正则提取 jest/vitest/mocha/pytest 风格摘要。
- **v1 不做结果缓存**：修复轮之间文件会变化，按文件列表缓存会重放陈旧结论。`changedFiles` 与 `force` 参数均被显式 `void` 掉。
- `unavailable` 永不判定产物失败，但**禁止 quick channel** 并强制完整复核。
- 快速通道（A4）：`review_hint === 'skip'` 且 `riskOf !== 'high'` 且机械验证开启且 compile+tests 全 pass → `exec/ok:DONE` 直接交付。

### 5.3 计划审计协商协议（v5.2）

配置 `stages.plan_audit`（≤2 个模型）即启用；缺省/空 = 功能关闭、零行为变化。

- **闸门位置**：计划围栏解析成功后不立即放行，而是把计划**停放**在 `task.pendingPlanAudit`（仅运行时字段），到 `agent/turn-stopping` 由 `runAuditGateIfPending()` 统一处理。
- **并行派发**：`dispatchPlanAuditors()` 为每个未熔断的审计员 spawn 一个子代理（同一 `outputSchema` 契约），`Promise.all` 收敛；单审计员超时/无结构化输出被丢弃，部分降级会打 warn。
- **保守并集仲裁（D1）**：同 id 问题取更严 severity；`passed` 需要「全体 passed ∧ 最低 confidence ≥ 0.7 ∧ 并集里无任何非 minor 问题」——审计员「pass 但带 major 问题」被视为不一致，保守处理为不通过。
- **协商回合（r≥2）**：审计员 prompt 附带上一轮问题 + 规划者响应（`adopted` / `rebutted`），要求逐条验证「已采纳是否真正修复」「反驳是否成立」，在 `rebuttal_verdicts` 给出 `accepted` 与 `note`；反驳需**全体审计员接受**才算成立。
- **预算复用（D2）**：审计不通过消耗 `plan_retry`（与 schema 校验失败同轨），耗尽走既有 `model/hard-fail` 终止链。
- **fail-open（设计 §6）**：审计员派发失败/超时/无结构化结论 → 放行本版计划并计 `auditSkipped`；审计员熔断时走其 `fallback_chain`，全不可用同样放行。**审计是增强不是阻塞。**
- **记账**：审计员 token 计入 `subTokens.auditor`，费用记在 plan 阶段；审计 step **不占**规划步数预算（`step/end` 处理时 `child.role !== 'auditor'` 才计）。
- **可观测**：每轮 `PlanAuditRound`（含 adopted/rebutted/passed）落入快照 `planAudit`，最终报告追加 `renderAuditNote`（`审计 N 轮（终判通过）｜审计放行 M 次`）。
- **prompt 前缀隔离**：审计员 prompt 以 `AUDIT_PROMPT_MARKER`（`你是独立的计划审计员`）开头，复核员以 `REVIEW_PROMPT_MARKER`（`你是独立的复核员`）开头——`handleUserInput` 靠前缀过滤，因为 `run.id` 与子会话 session id 不同，`childSessions` 映射挡不住子代理把 prompt 当用户消息回投（E2E 缺陷 #7）。

### 5.4 模型路由与降级链

`ModelRouter.resolve(stageKey, { role, risk, override })`（`router/model-router.ts:22`）：

1. 会话 override 先 `mergeOverride` 出临时配置。
2. `allowDegrade = !(stageKey === 'review' && risk === 'high')`（v5.0 §4.3：高风险禁止复核降级）。
3. `onFailure`：`role === 'fixer'` → 强制 `auto_degrade`（ADR #28：修复者降级而不继承 plan 的 hard_fail）；否则取阶段配置。
4. 主模型健康 → 直接返回主绑定。
5. 不健康 → `hard_fail` 或 `!allowDegrade` → `{ binding: primary, hardFail: true }`。
6. 否则遍历 `chainFor()`：fixer 角色优先 `execute.model`，其余取显式 `fallback_chain`，空则同族兄弟（plan/review 用 execute 模型，execute 用 review 模型 = v5.0 §6.2 混合默认）；返回首个健康者并标记 `degraded: true`；全不可用 → hardFail。

`bindingForState()`（状态 → 阶段映射）：`PLANNING/PLAN_FAIL/RE-PLANNING` → plan；`EXECUTING` + `fixEscalated` → `resolve('plan', { role: 'fixer' })`；`EXECUTING` → execute；`REVIEWING` → review；其余 → execute。

**effort 语义映射**（`router/effort.ts`）：内部枚举 `off|low|medium|high|max` → provider 线词汇。deepseek 家族**没有 `medium`**（`medium → high`）；glm/qwen/zhipu/kimi 的 `off` → `null`（清除为 provider 默认）；未知家族 pass-through。这解释了 README 里「settings 未声明 `reasoningEfforts` 档位的模型必须显式配 `reasoning_effort: off`」这条硬规则。

**健康服务**（`router/health.ts`，A6）：per `provider::model` 的 5min 滑动窗口，3 次失败置熔断，10min 后半开放行一次探测；**探测失败立即重关并重新计时**（否则 `at >= halfOpenAt` 会让后续所有请求通过，E2E 第 4 轮修复）；请求成功即清空窗口（`onRequest` 里 `health.recordSuccess`）。不持久化——重启后重新探测。

### 5.5 预算与熔断

**预算台账**（`budget/ledger.ts`，V7/A5/#27）：
- 单文件 `budget.json`，结构 `{ daily: {YYYY-MM-DD: {orchestrated, passthrough}}, tasks: {taskId: spend}, ledger: LedgerEntry[] }`；写临时文件后 `renameSync` 原子替换，读端永不见半写文件。
- `debit()` 顺序：任务限额（`task_limit_cny`，默认 5）→ 日限额（`daily_limit_cny`，默认 50）→ 累加 → 推 ledger（上限 5000 条，滚动保留 4000）→ flush。
- `pruneTasks(keep)` 丢弃不再活跃的任务条目（长驻宿主控制文件增长）；日总额是权威限额，per-task 仅诊断。
- **透传观测**：`observePassthrough` 只累计到 `daily.passthrough`，默认不计入硬上限（ADR #27）；passthrough 会话 id 进 `passthroughObserve`（上限 5000，超了整体清空）。
- **估价模式**：`Pricing.rate()` 只对 4 个 deepseek 模型有价目（v4-flash/v4-pro/deepseek-chat/deepseek-reasoner），未覆盖的模型 `cost = 0`。

**熔断器**（`circuit_breaker`，A12，在 `accountUsage` 里）：
| 触发 | 事件 |
| --- | --- |
| `ledger.debit` 返回 `ok=false` | `budget/exhausted` |
| 总 token > `total_tokens_max`（800000）或 `llmCalls` > `total_llm_calls_max`（40） | `circuit/broken` |
| `now - startedAt > wall_clock_max_min * 60000`（默认 30min） | `circuit/broken` |
| `router.bindingForState` 返回 `hardFail` | `model/hard-fail` |
| 复核派发超时两次 | `review/deadlock:EXEC`（保守执行缺陷） |

**请求失败自恢复**（`onRequestError`）：连续失败上限 3 次（`requestRetries`），期间返回 `{ kind: 'retry' }` 让宿主重试；第 3 次仍失败则放行内建错误处理，避免配置类错误造成无限重试风暴（E2E 缺陷 #1）。notice 按 key 去重（`noticeOnce`）。成功请求重置计数。

### 5.6 入口门禁（A9/A10）

`gate.decide({ text, forced, passthroughFlag })` 固定 7 步顺序：

| 步 | 规则 | 决策 |
| --- | --- | --- |
| 1 | `forced`（`/orch task`、`/per <文本>`） | orchestrate |
| 2 | `passthroughFlag`（`/orch passthrough`） | passthrough |
| 3 | 命中 `passthrough_patterns`（默认 `^(什么\|为什么\|怎么\|如何\|哪个\|是否\|能不能\|帮我看看\|解释\|翻译)`） | passthrough |
| 4 | 命中 `orchestrate_patterns`（默认 `(实现\|重构\|修复\|新增\|删除\|迁移\|编写\|开发\|优化)`） | orchestrate |
| 5 | `len <= short_len(40)` 且无修改意图动词 | passthrough |
| 6 | `len >= long_len(200)` | orchestrate |
| 7 | 默认 | `orchestrate`（保守） |

`handleUserInput` 的前置过滤：`message.source.kind !== 'user'` 直接返回（A8：插件来源永不重新门禁）；prompt 标记前缀放行；`registry.isChild(sessionId)` 放行。

### 5.7 事件总线与宿主接线

`engine.ts:1395` 的 `disposers` 一次性挂载 5 个宿主事件 + 1 个 effects + 命令 + system prompt：

| 宿主事件 | 处理器 | 职责 |
| --- | --- | --- |
| `session/event` | `onSessionEvent` | usage 记账、计划围栏检测、`[NEED_REPLAN]` 捕获、工具错误/diff 采集、step 审计轨迹 |
| `agent/inbox/claimed` | `handleUserInput` | 门禁、任务创建/入队、活跃任务的状态路由（见下） |
| `agent/request` | `onRequest` | `await next()` 后按状态重写绑定（provider/model/reasoningEffort）、健康恢复、`degradedStages` 审计 |
| `agent/request-error` | `onRequestError` | 健康记录、自恢复重试（≤3）、hardFail 中止 |
| `agent/turn-stopping` | `onTurnStopping` | **turn 驱动器**：按 state switch 决定 steer 或事件 |
| `subagent/start` | `registry.trackChild` | 子会话注册 |
| `ctx.effect` | — | 卸载时遍历 `disposers` 全部解绑 |

**活跃任务的用户输入状态路由（§9.2）**：
- `PLANNING` / `RE-PLANNING` / `IDLE`（排队）→ 覆写 `goal` 并重置 `stageSteps.plan = 0`
- `EXECUTING` → 推入 `userDirectives`（下一轮执行/修复指令注入）
- `REVIEWING` → 推入 `userDirectives`（下一执行轮生效）

**`onTurnStopping` 的 state switch 是插件的「主循环」**：

| state | 行为 |
| --- | --- |
| `PLANNING` | 审计门 → 步数超限（`plan/steps-exceeded` + `plan/retry`）→ 否则 steer 规划指令 |
| `PLAN_FAIL` | `plan/retry` → steer |
| `RE-PLANNING` | `replan_cycle > max`（**当前实现为恒假**，见方案 §P1-06）→ 审计门 → 步数超限（`replan/fail`）→ 否则 steer 重规划指令 |
| `EXECUTING` | `[NEED_REPLAN]` → `exec/need-replan`；`execErrorCount > 0` → `exec/fail`；步数超限 → `exec/steps-exceeded`；否则机械验证 → quick channel 或 `exec/ok`（→ 递归调用自身进 REVIEWING） |
| `REVIEWING` | `runReview`（派发 → 死锁/补证/路由）→ steer；无 steer 且非终态则注入「请继续」 |

### 5.8 任务队列与并发

- `TaskRegistry`：`byId`（任务表）、`activeBySession`（A8：sessionId → 活跃 taskId，**替换了无效的 `task:` 前缀过滤**）、`childSessions`（子会话集合）。`prune(retentionMs = 24h)` 清理终态任务（磁盘快照保留）。
- `TaskScheduler`（ADR #19）：`running` + `queue` 两个字段，`admit()` 满则排队，`finished()` 返回下一个；`positionOf()` 给排位。接口形态为将来并行留口，**但 `maxParallel` 构造参数完全未被使用**——始终单任务串行。
- 排队任务仍以 `IDLE` 留在 registry 中（`attach` 不进 `activeBySession`？—— 实际上 `attach` 对非终态即入 `activeBySession`，所以排队任务也会被 `handleUserInput` 当作活跃任务处理，只是 goal 覆写在 launch 时才生效）。
- 调度推进点：上一个任务 `settle()` 时 `scheduler.finished(task)` 返回的下一个任务立即 `transitionOrLog(next, 'task/launch')` 并注入启动 steer。

### 5.9 持久化与恢复

- **快照**（`persistence/snapshot.ts`，§9.4/V7）：`~/.dsh/storages/orchestrator/tasks/<taskId>.json`，`id` 经 `[^a-zA-Z0-9_-]` 清洗；写 `.tmp` 后 `renameSync`。`archive()` 是空实现（终态快照留盘供检查）。
- **恢复策略（v1：一律放弃）**：boot 时 `recover()` 遍历 `recoverable()`（非终态 ∧ 非 `abandoned`），为每个快照重建 `OrchestratorTask`（补齐 `planAudit`/`auditSkipped` 向后兼容），`abandoned = true` → `forceAbort('stale_snapshot')` → 落盘 → `registry.settle`。
  - **故意不做会话恢复 steer**：新宿主进程无法接续旧会话的 turn 循环（`engine.ts:1414` 注释）。
  - 中止结果持久化后，后续 boot 不再重复回收。
- **每次迁移都落盘**：`transitionOrLog()` 在 `transition()` 之后无条件 `snapshots.save()`；预算每次 `debit` 也同步 flush。**同步 I/O 在事件循环上**。

### 5.10 可见性（ADR #14）

三种输出通道，互不替代：

| 通道 | API | 语义 |
| --- | --- | --- |
| `notice` | `agent.inject(createUserMessage({ source: { kind: 'plugin', plugin: 'per', form: 'notice' } }))` | 只读信息，不改变模型行为；按 `(sessionId, key)` 去重 |

### 5.11 命令与设置界面

**`/orch`**（子命令：`status | set | reset | save | budget | task | passthrough | abort`）
- `set`：`plan=<model> execute=<model> review=<model>` → 写 `sessionOverrides`（`Map` 上限 5000）。

**设置界面**（`web/src/client.js`，495 行，React.createElement 手写，无构建步骤）：
- `inject: ['connection', 'settingsScope', 'slots']`，命名空间 `dsh-per`。

### 7.3 已知的行为偏差（详见优化方案）

1. `RE-PLANNING` 分支的 `replan_cycle > max` 恒假 → `replan/fail:EXHAUSTED` / `abortReplanExhausted`（里程碑「重规划轮次耗尽」）**不可达**。
2. `settle()` 里排队任务的启动通知用 `MILESTONES.executing(model, 0, '')`，产出「开始执行（model），计划 0 步」——任务实际刚进入 `PLANNING`。
3. `Gate` 构造函数对补丁里的正则**无 try/catch**，一条写错的 `passthrough_patterns` 会让插件启动即崩。
4. 子代理会话 id 在 `agents` 与 `lastBinding` 两个 Map 中**永不清理**（settle 只删根会话 id）→ 长驻宿主内存泄漏。
5. `PRICING` 只覆盖 deepseek 家族 → glm/qwen/kimi 等全部按 ¥0 记账，日限额护栏对其失效。
6. `transition-table.ts` 顶部注释称「先试守卫变体行再试精确行」，与 `fsm.ts` 实际实现（精确行优先）相反。
