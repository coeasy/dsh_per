## 1. P0 — 必须修

### P0-01 `engine.ts`（1487 行，全库 39%）零单元测试

- **现象**：72 个 `it()` 全部覆盖纯函数与 FSM；引擎（宿主接线、任务生命周期、review/audit 派发、turn 驱动、命令、system prompt）**完全依赖 E2E**。任何对引擎的改动都是盲改。
- **根因**：`createEngine(ctx, rawConfig)` 把宿主契约（`AnyCtx`/`AnyAgent` 全 `any`）、文件系统、`child_process`、`subagents` 派发与 `ctx.on` 订阅全部内联在同一个工厂函数体里，无法注入替身。
- **方案**：
  1. 新增 `src/host-contract.ts`：定义 `HostContract`（`on`/`get`/`inject`/`effect`/`logger`）、`SubagentRuntime`（`start`/`dispose`/`result`）、`CommandRegistry`、`SystemPromptSection`、`SettingsService`、`Logger` 五个接口。`createEngine` 改为 `createEngine(ctx: HostContract, rawConfig, deps?: Partial<EngineDeps>)`。
  2. 依赖注入四件套：`fsOps`（读写/重命名/mkdir）、`spawner`（机械验证）、`clock`（`Date.now`，便于测试熔断与保留窗）、`subagents`。
  3. 把引擎拆成 5 个可测单元并各自导出：`createGateRouter()`（门禁+预算预检+任务创建）、`createEventDriver()`（`onSessionEvent`/`accountUsage`）、`createTurnDriver()`（`onTurnStopping`/`runReview`）、`createReviewDispatcher()`、`createAuditGate()`。`engine.ts` 退化为装配文件（目标 < 300 行）。
- **涉及文件**：`src/engine.ts`、`src/host-contract.ts`（新）、`src/task/fsm.ts`（暴露 `transitionCore`）、`test/engine-gate.test.ts`、`test/engine-turn.test.ts`、`test/engine-review.test.ts`、`test/engine-budget.test.ts`、`test/engine-recover.test.ts`（新）
- **验收**：
  - 引擎相关单测 ≥ 30 个；`handleUserInput` / `onTurnStopping` / `onSessionEvent` / `accountUsage` / `dispatchReviewer` / `runAuditGateIfPending` / `recover` 各有 ≥ 1 个正常 + ≥ 1 个异常用例。
  - `vitest --coverage` line 覆盖率 ≥ 70%（阶段 A 结束）。
  - 既有 72 个用例与 `ci:checks` 全绿；`docs/E2E测试报告-v0.1.0.md` 的 5+5 场景行为逐字节不变。

### P0-02 ADR #18「修复升级」整条链路是死代码

- **现象**（`grep` 实测）：
  - `fix_loop.escalate_after_consecutive_fails`（默认 2）只在 `schema.ts:59/63` 出现，**无运行时读取方**。
  - `OrchestratorTask.computeEscalation(threshold)`（`fsm.ts:274`）**无任何调用方**。
  - `snapshot.fixEscalated` 只被**读**（`engine.ts:350`、`:394`、`:656`、`:694`）与**清**（`fsm.ts:237`，`clearFixEscalated`），**从未被置为 `true`**。
- **后果**：ADR #18 承诺的「同一 issue 连续失败 N 轮 → 升级由规划模型修复」从未生效；连带 `ModelRouter.resolve('plan', { role: 'fixer' })`（ADR #28：fixer 走 executor-first 降级链而非继承 plan 的 hard_fail）与 `fixRound(..., escalated)` 里程碑文案中的升级标注全部在暗处，且无测试覆盖。这是「文档承诺能力 ≠ 实际行为」的典型。
- **方案**：
  1. 在 `hooks.injectFixes`（`engine.ts:348`）中：`task.snapshot.fixEscalated = task.computeEscalation(effectiveConfig.fix_loop.escalate_after_consecutive_fails)`（`issueFailStreak` 已在 `recordStreaks` 中维护，M5 契约成立）。
  2. 保留 `replan/ok` 的 `clearFixEscalated`（`transition-table.ts:173`）——重规划后修复者不再升级。
  3. `buildFixDirective` 已读取 `fixEscalated` 追加「（本轮由规划模型升级修复）」，无需改动。
- **涉及文件**：`src/engine.ts`、`src/task/fsm.ts`
- **验收**：新增 3 个单测：
  1. 连续 2 轮出现同一 `issue.id` 且均 fail-exec → `snapshot.fixEscalated === true`；
  2. `replan/ok` 之后 `fixEscalated === false`；
  3. `fixEscalated === true` 时 `onRequest` 的绑定来自 plan 阶段且 `degradedStages` 记录为 `execute`（验证 ADR #28 的 fixer 分支）。

### P0-03 非 deepseek 模型成本记为 ¥0，日/任务限额护栏对它们失效

- **现象**：`engine.ts:52` 的 `PRICING` 表只覆盖 4 个 deepseek 模型；未命中时 `cost = 0`。E2E 报告自己也标了「mock 模型不在 PRICING 表 → 估价模式 cost=0，符合 v1 设计」，但 E2E 用的正是 `kimi-k2.5` + `glm-5` + `v4-flash`——**这意味着真实部署里 `daily_limit_cny: 5` / `task_limit_cny: 5` 对主力模型完全不起作用**，`budget/exhausted` 永不触发。
- **根因**：价格表硬编码在引擎里，没有配置入口，也没有「未知模型」的告警与降级策略。
- **方案**（两档，分阶段落地）：
  - **(a) 阶段 A — 可配置 + 告警**：
    1. schema 新增 `budget.pricing: Record<string, { input: number; output: number }>`（模型 id 或前缀 → 单价 CNY/百万 token），并支持 `DSH_HOME/storages/orchestrator/pricing.json` 覆盖；`PRICING.rate` 改为先查配置再查内置表。
    2. 内置表补齐 glm / qwen / kimi / deepseek 主流型号的公开牌价（标注来源与日期）。
    3. **未知模型一次性告警**：首次遇到未计价模型时 `noticeOnce(sessionId, 'pricing:' + model, '【编排】模型 X 无价格表，成本按 ¥0 记账，日限额护栏对该模型不生效；请在 budget.pricing 配置单价')`。
    4. `ledger.debit` 返回增加 `priced: boolean`。
  - **(b) 阶段 B — 双轨护栏**：
    1. 未计价模型改走 **token 预算**（`budget.task_tokens_max` / `budget.daily_tokens_max`）而非金额预算，金额仅观测。
    2. `/orch budget` 与最终报告分列「实价 / 估价 / 未计价」三类金额。
- **涉及文件**：`src/engine.ts`、`src/budget/ledger.ts`、`src/config/schema.ts`、`src/visibility/milestones.ts`、`test/units.test.ts`
- **验收**：
  - 配置 `budget.pricing: {'zhipu/glm-5': {input: 2, output: 8}}` 后，glm 任务的 `spentCny > 0` 且 `task_limit_cny: 0.01` 能触发 `budget/exhausted`；
  - 未知模型触发一次 notice 且日志可见；
  - `/orch budget` 输出三类金额分列（阶段 B）。

### P0-04 同一 task 的 `transition()` 无整体串行化（并发双写）

- **根因**：`OrchestratorTask.enqueue()`（`fsm.ts:113`）**只串行化 hook 执行**；而 `snapshot.state = chosen.to` 与 `applyAction()`（计数器自增、`recordStreaks`、`replacePendingFixes`、`planVersion++`）在 `transition()` 主体内同步完成。引擎有 4 个异步入口可指向同一 task：
  - `session/event` → `accountUsage` → `transitionOrLog(task, 'budget/exhausted' | 'circuit/broken')`
  - `agent/turn-stopping` → `onTurnStopping` → 多条 `transitionOrLog`
  - `agent/request-error` → `transitionOrLog(task, 'model/hard-fail')`
  - `subagent/start` / review 派发返回 → 状态相关副作用
  JS 事件循环允许这些在微任务边界交错（`transition` 内部无 `await`，但其调用点是异步的），因此两个调用可读到同一 `state` 并各自完成 `applyAction`。
- **后果**：计数器双自增（`fix_cycle`/`replan_cycle` 超预算误判）、state 被后写者覆盖（例如 `exec/fail` 与 `budget/exhausted` 竞争导致终态判定错乱）、`recordStreaks` 对同一 verdict 重复记账。
- **方案**：把整个迁移包进 per-task 队列——`transition(event, depth = 0)` 改为 `this.enqueue(() => this.transitionCore(event, depth))`，`transitionCore` 保留原有实现（含回退链递归，全部在同一队列槽内完成）。`forceAbort` 同样入队。对外签名与语义不变。
- **涉及文件**：`src/task/fsm.ts`
- **验收**：新增单测——对同一 task 连续 `Promise.all` 触发 `exec/fail` 与 `budget/exhausted`（或 `circuit/broken` + `user/cancel`），断言：
  - 计数器增量精确（无双自增）；
  - 最终 `state` 唯一且符合先入者语义；
  - `illegalTransitions` 未因竞态误增；
  - `snapshot.reviewHistory` 无重复条目。
  既有 `fsm.test.ts` 14 个用例全绿（迁移语义未变）。

## 2. P1 — 高优先

### P1-05 `RE-PLANNING` 耗尽分支不可达（off-by-one）

- **根因**：`engine.ts:1058` 用 `snap.counters.replan_cycle > effectiveConfig.limits.replan_cycle_max`（严格大于）；而表内所有递增 `replan_cycle` 的行都带 `guard: replan_cycle < max` + `action: replan_cycle++`（`transition-table.ts:138/152/158/213`）→ `replan_cycle` 恒 ≤ `max` → 该判断**恒假**。
- **后果**：`'replan/fail:EXHAUSTED'` 行（`transition-table.ts:182`，guard `>= max`）只由引擎显式指名，永不发生；hook `abortReplanExhausted` 与里程碑「重规划轮次耗尽」是死代码。实际耗尽路径走 `exec/defect:EXHAUSTED` / `review/fail-plan:DONE` → `DONE_FLAGGED`，与文档描述不一致（结果仍收敛，但语义错位且不可观测）。
- **方案**：把判断改为 `>= max`（保留「重规划轮次耗尽」的独立里程碑语义）。**不**改为删除该行——`DONE_FLAGGED` 与 `ABORTED` 的区分对用户有意义（前者有产物、后者无）。
- **涉及文件**：`src/engine.ts`、`src/task/transition-table.ts`
- **验收**：新增 FSM 单测——`replan_cycle` 打到上限后，`RE-PLANNING` 的 turn 边界触发 `replan/fail:EXHAUSTED` → `ABORTED`，且 hook `abortReplanExhausted` 被调用一次。

### P1-06 `plan_protocol` 死配置

- **现象**：`schema.ts:34` 声明 `plan_protocol: 'builtin' | 'fenced'`（ADR #26），运行时只有 fenced 路径；`grep plan_protocol src/` 仅命中 schema 与测试断言。
- **方案**：删除该键（推荐——减少配置面与认知负担），并同步 README 与设置界面文案（当前设置界面不暴露该键，无需改 UI）。若保留，则必须实装 `builtin`（`plan/ok` 直连、无围栏协议）并加测试。
- **涉及文件**：`src/config/schema.ts`、`README.md`、`test/units.test.ts`
- **验收**：`grep plan_protocol src/` 无命中；`vitest run` 全绿。

### P1-07 无守卫的精确行会静默屏蔽变体行（迁移表脆弱点）

- **现象**：`fsm.transition` 的行解析是「精确行优先，再按定义顺序试变体」（`fsm.ts:140` 注释明确）。`exec/ok`（**无守卫**）因此永远优先于 `exec/ok:DONE`（有守卫）——引擎靠**显式发复合事件名**（`engine.ts:1105`）绕开。这条约定完全靠人肉记忆，`ci-checks` 不检查。
- **对照**：`review/pass` 精确行**有守卫**（`!mechanicalFailedAfterPass`），所以 `review/pass:MISS` 能正常工作。同一张表里两种范式并存，且 `transition-table.ts:79-83` 顶部注释写的是「先试守卫变体行再试精确行」——**注释与实现相反**。
- **方案**：
  1. `ci-checks.mjs` 增加**第 5 项不变量**：对每个 `${event}:variant` 行，若同一 state 存在**无守卫**的精确 `event` 行，则从 `src/engine.ts` 静态扫描事件名字符串集，要求该复合事件名被显式发射；否则 FAIL 并打印「死行」。
  2. 统一 `transition-table.ts` 顶部注释与 `fsm.ts` 注释为「精确行优先」。
- **涉及文件**：`scripts/ci-checks.mjs`、`src/task/transition-table.ts`、`src/task/fsm.ts`
- **验收**：`pnpm run ci:checks` 通过；故意把一个复合事件的引擎发射点删掉后，门禁 FAIL 并指出具体死行。

### P1-08 子代理会话 id 在 `agents` / `lastBinding` 永不清理

- **根因**：`settle()`（`engine.ts:253`）只按 `task.snapshot.sessionId`（根会话）清理 `agents`/`lastBinding`/`noticedOnce`/`requestRetries`；而子代理会话同样会：
  - 在 `handleUserInput` **顶部**（`engine.ts:421`，早于 `registry.isChild` 早退）执行 `agents.set(agent.id, agent)`；
  - 在 `onRequest`（`engine.ts:652`）执行 `lastBinding.set(sessionId, ...)`。
  因此每个 reviewer/auditor 派发都在这两个 Map 中留下永久条目。`childSessions`（engine 侧）在 settle 时按 taskId 清理，所以只有「子会话 → 角色」映射是干净的。
- **后果**：长驻宿主每轮 review + 2×audit 派发永久增加 ~3 个 Map 条目；更糟的是 `notice()` 会按 sessionId 查 `agents`，可能把里程碑注入到早已结束的会话。
- **方案**：
  1. `settle()` 遍历 `childSessions` 匹配 taskId 时，同步 `agents.delete(sid)`、`lastBinding.delete(sid)`、`requestRetries.delete(sid)`、`noticedOnce.delete(sid)`。
  2. `onRequest` 对 child 会话**不写** `lastBinding`（stage 直接由 `childSessions.get(sessionId).role` 推出），避免子代理污染父会话绑定。
  3. `agents` 增加与 `passthroughObserve` 同款的 5000 上限 + 清尾策略（保持一致的「有界内存」约定）。
- **涉及文件**：`src/engine.ts`
- **验收**：新增单测——模拟 N=50 轮（review + 2 auditor）派发，断言 `agents.size` 与 `lastBinding.size` 不随 N 增长（终态后回到基线）。

### P1-09 `Gate` 坏正则炸整个插件

- **根因**：`gate.ts:22-23` 的 `new RegExp(p, 'u')` 无 try/catch；gate 配置只走补丁层（用户在 `cordis.patch.yml` 手写），一条拼错的正则（如 `(^abc`）会让 `createEngine` 抛异常 → 插件启动即崩，且报错栈不指向具体哪条 pattern。
- **方案**：构造时对每条 pattern 单独 try/catch；失败项 `logger.warn('gate: invalid regex "%s", skipped: %s')` 并跳过；若两类 pattern 全部失效则回退内置默认值并 warn。
- **涉及文件**：`src/gate/gate.ts`、`test/units.test.ts`
- **验收**：`new Gate({ passthrough_patterns: ['(^abc'], orchestrate_patterns: ['(实现)'], ... })` 不抛异常，`(实现)` 仍生效；新增 2 个单测（单条失效 / 全部失效回退默认）。

### P1-10 复核 prompt 无 token 预算约束；分片复核（M3）就绪但未接线

- **根因**：`buildReviewPrompt`（`engine.ts:711`）无条件 `JSON.stringify` 完整计划 + 全部历史 issues + 补证问题；`review.input_token_budget`（默认 50000）声明后无读取方（`schema.ts:48`）；`mergeShardedVerdicts`（`review.ts:81`，M3）已导出并有单测，但引擎始终单片派发。
- **后果**：大计划/大 diff 任务的复核 prompt 可轻松超过复核模型的上下文上限，导致 `stopReason !== 'completed'` → 死锁 → 保守合成缺陷 → 无谓修复轮。这是「复核死锁」在真实大任务上的最可能成因，且当前无指标可归因。
- **方案**：
  1. **预算裁剪**（必做，成本低）：`estimateTokens(reviewPrompt) > input_token_budget` 时降级为骨架计划（仅 steps 的 `id`/`title`/`files`，丢 `risk_note`），历史 issues 只保留最近 2 轮。
  2. **分片复核**（增强）：`changedFiles` 超过阈值（如 12 个文件或 diffLines > 800）时按文件分片并行派发多个 reviewer，`mergeShardedVerdicts` 合并（保守取最严 defect、最低 confidence、id 去重后缀）。分片数上限 4，受 `circuit_breaker.total_llm_calls_max` 约束。
  3. prompt 与机械验证结果分列统计 token，写入 `snapshot.subTokens` 的 `reviewer` 分项，便于复盘。
- **涉及文件**：`src/engine.ts`、`src/protocols/review.ts`、`src/config/schema.ts`
- **验收**：
  - 单测：构造 6 万 token 的计划，断言 `estimateTokens(buildReviewPrompt(...)) ≤ input_token_budget`；
  - 单测：>1 分片时合并结果 `pass = all shards pass`、`defect_type` 取最严、`confidence` 取最小、重复 id 加 `-chunkN` 后缀；
  - E2E 新增「大 diff 分片复核」场景。

### P1-11 `concurrency.max_parallel_tasks` 配置无效

- **现象**：`engine.ts:113` 把该值传入 `TaskScheduler` 构造，但 `TaskScheduler`（`registry.ts:80`）只有 `running: OrchestratorTask | null` 一个槽，**构造参数完全未使用**。设置 `max_parallel_tasks: 4` 静默无效。
- **方案**（二选一，推荐 ①）：
  1. **① v1 语义收敛**：删除该配置键，README 明确「v1 严格串行（ADR #19）」；`TaskScheduler` 构造参数一并删除。
  2. **② 实装会话级并行**：`running` 改为 `Map<sessionId, task>`，会话内串行、跨会话并行；同时复核预算/熔断的任务级隔离（`ledger` 已按 taskId 记账，但 `accountUsage` 的熔断判断用的是单 task 快照，需确认跨会话无串扰）。
- **涉及文件**：`src/config/schema.ts`、`src/task/registry.ts`、`README.md`
- **验收**：① 删除后 `grep max_parallel_tasks` 仅 `package.json`（若有 fixture）命中；② 或新增单测：两会话各 1 任务并发运行，`budget.json` 中两个 taskId 独立累计。

### P1-12 排队任务启动通知文案错误

- **根因**：`engine.ts:271` 对 `settle()` 里接续的排队任务调用 `MILESTONES.executing(model, 0, '')` → 输出「【编排】开始执行（model），计划 0 步」；但此时任务刚 `task/launch` 进入 `PLANNING`，计划还不存在，`steps=0` 是假信息。
- **方案**：新增 `MILESTONES.launching(goal, queueNote?)`（如「【编排】排队任务启动：<goal 前 60 字>（原排位 N）」）用于此处；`executing` 保留给真正进入执行阶段（`plan/ok` 之后）的通知。
- **涉及文件**：`src/engine.ts`、`src/visibility/milestones.ts`、`test/units.test.ts`
- **验收**：快照测试断言排队任务启动通知不含「计划 0 步」；既有 `doneFlagged`/`reviewResult` 里程碑测试不受影响。

### P1-13 每次迁移/记账都做同步磁盘 I/O

- **根因**：`transitionOrLog`（`engine.ts:402`）在 `transition()` 之后**无条件** `snapshots.save()`（`writeFileSync` + `renameSync`）；`BudgetLedger.flush()` 每次 `debit` 也同步写。事件循环上的同步文件写；热路径上每次 LLM 调用至少 2 次。
- **方案**：
  1. `SnapshotStore` 与 `BudgetLedger` 都改为「脏标记 + 尾写」：`save()`/`debit()` 只置 dirty 并调度 `setImmediate` 合并写；同一 tick 内多次变更合并为一次写。
  2. 写入节流：快照 100ms、预算 250ms（金额累计可容忍微延迟）。
  3. 退出前 flush：挂到 `ctx.effect` 的清理回调，且监听 `process.once('exit')` 兜底（headless 一次性模式）。
- **涉及文件**：`src/persistence/snapshot.ts`、`src/budget/ledger.ts`、`src/engine.ts`
- **验收**：单测——连续 20 次 `transition` + 20 次 `debit`，mock fs 计数的实际 `writeFileSync` 次数 ≤ 6；进程退出回调触发后无 dirty 残留（快照内容与内存一致）。

### P1-14 机械验证不可取消；`summarizeTests` 误用于 compile；`lint` 死配置

- **根因**：
  1. `MechanicalVerifier.run(changedFiles, force)` 无 `AbortSignal`；`user/cancel` 中止任务后编译子进程仍跑满 `timeout_ms`（默认 120s），headless 进程被拖住。
  2. `runOne`（`mechanical.ts:94`）对 compile 与 tests 都调 `summarizeTests(out)`——编译输出若出现「1 passed」字样会产生误导性 summary。
  3. `mechanical_verification.commands.lint`（`schema.ts:72`）声明后从不执行。
- **方案**：
  1. `run(files, opts?: { signal?: AbortSignal })`，`signal.addEventListener('abort', () => child.kill('SIGKILL'))`；`runReview` 与 quick-channel 路径传入 `payload.signal`。
  2. `summarizeTests` 仅对 `tests` 命令调用；compile 只保留 `tail`。
  3. 实装 `lint`（走同一 `runOne`，结果并入 `MechanicalResult.lint`），quick channel 判定改为 compile/lint/tests 三项全 pass。
- **涉及文件**：`src/protocols/mechanical.ts`、`src/engine.ts`、`src/config/schema.ts`、`src/types.ts`
- **验收**：单测——abort 后子进程在 <1s 内被杀（用 `child_process.spawn('sleep 30')` 模拟）；compile 结果无 `summary` 字段；lint 命令执行并计入 `MechanicalResult`，fail 时禁止 quick channel。

### P1-15 `stale_snapshot` 中止原因映射错误

- **根因**：`AbortReason` 含 `'stale_snapshot'`（`types.ts:231`），但 `forceAbort` 的 hook switch（`fsm.ts:181`）只映射 budget/user/circuit/model 四种，其余（含 `stale_snapshot`、`guard_chain_overflow`、`guard_rejected`、`replan_exhausted`）一律落 `abortGeneric`，里程碑文案为「守卫链溢出」。**boot 时 `agents` 为空所以用户看不见**，但快照里的中止原因与文案语义不符，排障时严重误导。
- **方案**：新增 `abortStaleSnapshot` hook（文案「宿主重启前的残留任务已放弃（v1 不恢复旧会话）」）并加入 switch；同时把 `guard_chain_overflow` 与 `guard_rejected` 拆成两个 hook，避免所有守卫类失败共用一句文案。
- **涉及文件**：`src/engine.ts`、`src/task/fsm.ts`、`src/types.ts`
- **验收**：单测——`recover()` 后快照 `state=ABORTED`、`abandoned=true`，里程碑文案不含「守卫链溢出」；`transition('plan/ok')` 在 `guard_rejected` 下的文案独立可辨。

### P1-16 无 CI workflow / 无 lint 配置 / 无发布守门

- **现状**：无 `.github/workflows`；`settings/namespace.ts:40` 有 `// eslint-disable-next-line @typescript-eslint/no-explicit-any` 注释但**全库无 eslint 配置**；无 `prepublishOnly`；`lib/`（84 个构建产物）与 `web/dist/` 已入库。
- **方案**：
  1. 新增 `.github/workflows/ci.yml`：`pnpm install --frozen-lockfile` → `tsc --noEmit` → `vitest run` → `node scripts/ci-checks.mjs`（矩阵 node 22 / 24）。
  2. 单工具 lint+format：`biome`（零配置依赖，与现有零 bundler 理念一致）或 `eslint` + `prettier` 二选一；`package.json` 加 `lint` / `format` script。

- **涉及文件**：`.github/workflows/ci.yml`（新）、`biome.json` 或 `eslint.config.js`（新）、`package.json`、`.gitignore`（新）、`CHANGELOG.md`（新）、`README.md`
- **验收**：PR 上四项门禁自动跑并阻塞合并；`npm pack` 内容恰为 `lib/`、`cordis.patch.yml`、`web/dist/client.js`；`pnpm publish --dry-run` 无异常。

### P1-17 宿主契约全 `any`，且无启动能力探测

- **根因**：`AnyCtx`（`engine.ts:44`）与 `AnyAgent`（`:43`）大量 `any`；`ctx.get('subagents' | 'commands' | 'systemPrompt' | 'agentDefaultModel' | 'settings')` 鸭子类型；能力缺席时静默降级（settings 降级有 warn，但 `subagents` 缺席只在派发时以「subagents service missing」表现为死锁）。
- **后果**：TS 在插件↔宿主边界完全无保护；宿主升级改名时插件编译期无感知；缺 `subagents` 的部署会让**每个任务在复核阶段永远死锁**（走满 fix loop → DONE_FLAGGED），且没有任何启动告警。
- **方案**：
  1. 新增 `src/host-contract.ts` 定义全部宿主接口（见 P0-01），`createEngine(ctx: HostContract, ...)`。
  2. boot 时能力探测：检查 `subagents.start` / `commands.register` / `systemPrompt.section` / `settings.register` / `agentDefaultModel`，缺失项写入 `engine.capabilities` 并在启动日志打 warn（`orchestrator: subagents service missing — review/audit disabled, quick channel only`）。
  3. 缺 `subagents` 时：review 阶段直接跳过（`review_hint=skip` 等价处理），并在最终报告标注「复核未执行（宿主不支持子代理）」。
- **涉及文件**：`src/engine.ts`、`src/host-contract.ts`（新）
- **验收**：`tsc` 通过且 `AnyCtx`/`AnyAgent` 从导出中移除；缺 `subagents` 的 mock 宿主启动日志含明确 warn，任务可经 quick channel 走到 DONE。

### P1-18 README / 版本 / 变更历史漂移

- **现象**：README 称「vitest（58 用例）」，实际 72 个 `it()`；`package.json` 版本 0.1.0 而设计已到 v5.3；README「已知限制」未收录本方案发现的项（如 `max_parallel_tasks` 无效、非 deepseek 成本 ¥0）；无 `CHANGELOG.md`。

### 5.2 新增门禁规则（`scripts/ci-checks.mjs`）

- **第 5 项：变体行可达性**——对每个 `${event}:variant` 行，若同 state 存在**无守卫**的精确 `event` 行，则要求该复合事件名在 `src/` 中被显式发射（静态扫描字符串集），否则 FAIL。
- **第 6 项：配置键必须被消费**——扫描 `config/schema.ts` 中所有叶子键名，要求在 `src/` 其他文件中至少出现一次引用（排除 schema 自身与 settings namespace 的透传键），未消费则 FAIL 并列出。此项会一次性捕获本方案 §7.2 的全部死配置，防止回归。

### 5.3 关键验收用例清单（阶段 A）

| 用例 | 断言 |
| --- | --- |
| 修复升级触发 | 同一 `issue.id` 连续 2 轮 fail-exec → `fixEscalated === true`；下一请求绑定到 plan 模型且走 fixer 降级链 |
| 升级清零 | `replan/ok` 后 `fixEscalated === false` |
| 非 deepseek 限额生效 | 配置 glm 单价后 `task_limit_cny: 0.01` 触发 `budget/exhausted` |
| 未知模型告警 | 首次遇到未计价模型只 notice 一次 |
| 并发迁移无竞态 | `Promise.all([transition('exec/fail'), transition('budget/exhausted')])` → 计数器精确、终态唯一、无重复 streak |
| 重规划耗尽可达 | `replan_cycle === max` 时 RE-PLANNING turn 边界 → `ABORTED` + `abortReplanExhausted` |
| 残留任务文案 | `recover()` 后里程碑不含「守卫链溢出」 |
| 排队任务启动文案 | 不含「计划 0 步」 |
