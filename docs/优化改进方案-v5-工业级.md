# dsh-per 工业级优化改进方案（v5）

> 制定日期：2026-09-06 ｜ 基线：`dsh-per@0.4.0`（commit `749a840`：151 用例全绿、ci-checks 7 项不变量、tsc 干净、CI workflow 在跑）
> 定位：前三轮方案（v1 死代码/护栏 → v2/v3 重构接线 → v4 打磨）解决的是「对不对」；本方案解决「**够不够工业级**」——按可长期运维、可交付第三方、可回归保障的工程标准补齐保障面，并以 **1.0.0** 作为工业级出口版本。
> 每项含：现状证据（文件:行 / 实测）→ 方案 → 验收标准。

---

## 0. 工业级判据与当前评分

| 维度 | 判据 | 现状（0.4.0） | 评分 | 目标 |
| --- | --- | --- | --- | --- |
| 功能正确性 | 核心链路贯通、无声明≠实现 | ✅ 4 轮清理后死配置/死代码为 0，ci-checks 7 不变量机械背书 | A | 保持 |
| 测试保障 | 覆盖率门禁、静态分析、E2E 自动化 | ❌ 无覆盖率统计（无 vitest.config）、无 lint、E2E 仅存报告未固化 | **C** | A |
| 可观测性 | 任务级事件轨迹、诊断命令、日志规范 | ❌ 快照是唯一记录（P2-11 两次延期）、无 /orch diag、日志无 taskId 约定 | **C** | A |
| 健壮性与安全 | 恢复输入校验、供应链检查、漏洞上报 | ⚠️ recover() 对损坏快照只做 JSON 级 try/catch（字段级无校验）；无 pnpm audit、无 SECURITY.md | C+ | A |
| 发布工程 | 发布流水线、元数据完整、版本策略 | ⚠️ 无 release workflow、package.json 无 engines/repository（`package.json`）、无 1.0 判据 | C+ | A |
| 性能与资源 | 同步 I/O 节流、内存有界 | ✅ 快照节流（终态同步）、内存有界清理、ledger 30 天窗 | A- | 保持 |
| 文档与可维护性 | 配置参考、CHANGELOG、CI 徽章、架构图同步 | ⚠️ 67 个配置键无统一参考文档；README 配置示例未覆盖 v3/v4 全部新键 | B- | A |

**结论**：功能面已达工业级，**保障面（测试/观测/发布）是短板**。本方案 18 项（G1–G18），分四个批次，全部完成后打 **1.0.0**。

## 1. 批次 A — 质量门禁（测试保障达标）

### G1 覆盖率统计与门禁 ⛔ 1.0 前必做
- **现状**：仓库无 `vitest.config.*`（实测），`package.json` 无 coverage 脚本；151 用例的质量没有量化下界。
- **方案**：新增 `vitest.config.ts`（`coverage: { provider: 'v8', include: ['src/**'], exclude: ['src/probe*','scripts/**'] }`，devDeps 加 `@vitest/coverage-v8`）；`package.json` 加 `"test:coverage": "vitest run --coverage"`；CI 增加覆盖率步骤。阈值起步 `lines ≥ 75%`，批次 D 后提到 `≥ 80%` 并写死在配置里防回退。
- **验收**：CI 输出覆盖率报告并执行阈值；本地 `pnpm run test:coverage` 可跑。

### G2 静态分析（lint + format）
- **现状**：无任何 linter（`grep eslint biome` 均空）；v4 已知 `MILESTONS` 类拼写问题靠人眼。v2 时决策「不引入 linter」在工业级标准下不成立。
- **方案**：引入 **biome**（单 devDep，lint+format 一体，零配置起步，符合本项目零 bundler 理念）：`biome.json`（建议规则：noExplicitAny=warn、useConst、noFloatingPromise 插件可后续）、`package.json` 加 `"lint": "biome check src test scripts"`、`"format": "biome format --write"`；CI 在 type-check 前加 lint 步骤；存量违规一次性 `format` + 按 warn 收敛。
- **验收**：`pnpm run lint` 零 error；CI 红灯可阻塞。

### G3 `exactOptionalPropertyTypes: true` 收紧（旧 P2-13 复活）
- **现状**：`tsconfig.json` 关闭该选项，可选字段类型不严格（`lastReviewError?`、快照可选字段等都有隐患面）。
- **方案**：单独提交打开开关，修复编译错误（预计集中在快照构造、`delete x.y` 模式、`exactOptional` 传参）；不改任何运行时行为。
- **验收**：`tsc --noEmit` 干净；151 用例回归不变。

### G4 CI 矩阵 + Node 版本契约
- **现状**：`.github/workflows/ci.yml` matrix 仅 `['22.x']`；`package.json` 无 `engines`（实测）——宿主最低 Node 版本无契约。
- **方案**：matrix 扩为 `['20.x', '22.x', '24.x']`；`package.json` 加 `"engines": { "node": ">=20" }`（`fs.renameSync`/structuredClone/setImmediate 均为 Node 20 稳定面）。
- **验收**：三个 Node 版本 CI 全绿；`npm i` 在 Node <20 有 engines 警告。

### G5 未知配置键告警（zod strip 的静默面）
- **现状**：zod 对未知键 strip（宽容是刻意的，v1 P1-06 验收），但用户拼错键名（如 `budget.pricing_unknown` 写成 `pricing-unknown`）完全无感知。
- **方案**：`createEngine` 对 rawConfig 做已知顶层/嵌套键 diff（复用 ci-checks 第 7 不变量的键集提取逻辑，抽到 `src/config/keys.ts` 共享），未知键 `logger.warn` 一次（noticeOnce 语义）。
- **验收**：单测——含未知键的 patch 启动时产生 warn 日志；已知键零误报。

## 2. 批次 B — 可观测性（运维达标）

### G6 快照版本化 + 恢复健壮性 ⛔ 1.0 前必做
- **现状**：`TaskSnapshot`（`types.ts:181`）无版本字段；`recoverable()` 对损坏 JSON 有 try/catch，但**字段级无校验**——半写/旧格式/外力篡改的快照（如 `counters` 缺失、`plan` 为字符串）会让 FSM 在恢复后以未定义行为运行；兼容靠 `recover()` 里零散的 `?? 默认值`。
- **方案**：
  1. `TaskSnapshot` 增加 `snapshotVersion: number`（构造器写 1）；
  2. 新增 `src/persistence/validate.ts`：`normalizeSnapshot(raw): TaskSnapshot | null`——关键字段（id/sessionId/state/counters 各键/stageSteps/planAudit 数组）逐一校验 + 补默认，非法返回 null；
  3. `recover()` 用 normalize；null 快照**改名隔离**为 `<id>.json.corrupt` + warn，不 crash、不占用调度器；
  4. `ci-checks` 增加第 8 项不变量：`snapshotVersion` 字段存在于 types 并在构造器写入（防新快照漏标）。
- **验收**：单测——损坏快照（缺 counters / state 非法 / 半写 JSON）三类输入下 recover 不 crash 且隔离文件存在；正常快照 roundtrip 无损。

### G7 任务级事件流（旧 P2-11 转正）⛔ 1.0 前必做
- **现状**：快照是唯一审计记录，中途变更只有最终态可查（两次方案延期，工业级运维必须可回放）。
- **方案**：`src/persistence/events.ts`：`EventStream.append({at, taskId, event, from, to, counters, fallbackChain})` 写 `<dataDir>/tasks/events.jsonl`（追加写、5MB 滚动保留 2 份）；引擎 `transitionOrLog` 与 `forceAbort` 路径打点（**所有迁移在 engine.ts 一处打点**，不破坏架构约束）；`events.enabled` 配置（默认 true，可关）。
- **验收**：单测——驱动一个完整任务，events.jsonl 行数与迁移次数一致、顺序正确；滚动触发时旧文件改名保留。

### G8 `/orch diag` 诊断命令
- **现状**：`/orch status` 只有运行摘要（`engine/commands.ts:57`）；排障需要手工翻 budget.json/快照。
- **方案**：新增 `diag` 子命令：健康窗口（熔断中的模型 + halfOpenAt）、今日/任务预算明细（三类金额：实价/估价/未计价计数）、活动任务的 lastReviewError / degradedStages / fixEscalated / 审计放行计数、事件流最近 N 行摘要。
- **验收**：单测——人为制造熔断 + 降级 + lastReviewError 后 `/orch diag` 全部可见。

### G9 日志规范：统一前缀 + taskId 关联
- **现状**：引擎日志均为 `orchestrator: …` 前缀（好），但多数调用点不携带 taskId（如 `engine/request.ts` 的 hard-fail 路径），长驻宿主多任务并发时无法按任务过滤。
- **方案**：约定「凡涉及任务的日志必须含 `(${task.id})`」；grep 全部 `logger.(warn|error|info)` 调用点补齐；写入 README 开发节与 biome 检查不可行（字符串规则），改为 `ci-checks` 第 9 项轻量静态检查：src 内 logger 调用若出现在有 `task` 标识符作用域的函数里则须包含 `task.id`（简化为注释豁免清单）。
- **验收**：grep 实测全部任务相关日志带 taskId；门禁通过。

## 3. 批次 C — 发布工程与文档

### G10 release workflow + 包元数据
- **现状**：无 release workflow（`.github/` 仅 ci.yml）；`package.json` 无 `repository`/`bugs`/`keywords`/`engines`；`prepublishOnly` 已有（build+test+ci:checks）。
- **方案**：
  1. `.github/workflows/release.yml`：push tag `v*` → 全量门禁 → `npm publish --provenance`（NPM_TOKEN secret）→ GitHub Release 附加 CHANGELOG 该版本段落；
  2. `package.json` 补 `repository`（github.com/coeasy/dsh_per）、`bugs`、`keywords`（['dsh','cordis','orchestrator','multi-model']）、`engines`（G4）。
- **验收**：tag dry-run（workflow_dispatch + `--dry-run`）产出可校验；`npm pack` 内容 = files 声明。

### G11 依赖供应链检查
- **现状**：无 audit 步骤（运行时依赖仅 3 个，风险低但无门禁）。
- **方案**：CI 加 `pnpm audit --prod --audit-level high` 步骤（fail on high+）；lockfile 已 gitignore（库包策略保留）。
- **验收**：CI 步骤存在且当前全绿。

### G12 全配置参考文档 `docs/CONFIG.md` ⛔ 1.0 前必做
- **现状**：67 个配置键散落在 README 示例 + 代码注释里（grep 实测 README 仅覆盖部分 v3/v4 新键）；第三方部署无法只看文档完成配置。
- **方案**：新增 `docs/CONFIG.md`——按层级列出全部键：名称/类型/默认值/语义/生效层（补丁/settings UI/会话 override）/行为示例。用脚本从 schema 抽取骨架 + 人工补语义描述；`ci-checks` 第 10 项：CONFIG.md 必须覆盖第 7 项不变量提取出的全部键名（文档漂移即红灯）。
- **验收**：`ci:checks` 10 项通过；README 配置节链接 CONFIG.md。

### G13 SECURITY.md + CONTRIBUTING（轻量）
- **方案**：`SECURITY.md`（漏洞上报邮箱/流程/响应时限承诺）、`CONTRIBUTING.md`（分支/门禁/CHANGELOG 要求，半页以内）；README 加 CI badge（`coeasy/dsh_per` actions）。
- **验收**：文件存在；badge 渲染。

### G14 架构图与模块图同步
- **现状**：v1 文档的架构图仍画 `src/engine.ts（1487 行胶水层）`，与当前 698 行 + 14 模块不符（文档漂移，v3 只更新了文字）。
- **方案**：更新 v1 图为双栏（核心 + engine/ 模块清单）并在 `docs/ARCHITECTURE.md` 落一份独立速览（v1 超长，新人入口应短）。
- **验收**：ARCHITECTURE.md 与 `ls src/engine` 实际文件一一对应（门禁不必查，PR 自查）。

## 4. 批次 D — E2E 固化（最大的测试保障缺口）⛔ 1.0 前必做

### G15 E2E 场景自动化（三次挂账的「E2E 重跑」的工程化解法）
- **现状**：`docs/E2E测试报告-v0.1.0.md` 的 5 业务 + 5 审计场景依赖外部 DSH 宿主 + mock 网关（端口 8399）+ `probe.patch.yml`，**不可在 CI 运行**，重构后一直只靠引擎单测背书。
- **方案**（不依赖真实宿主）：把 E2E 场景固化为 `test/e2e/pipeline.e2e.test.ts`——用 `engine-harness`（mock 宿主，已覆盖 5 类宿主事件）+ **进程内 mock 模型网关**（模拟 assistant/message 带 usage、tool/result、`[NEED_REPLAN]`、复核 verdict 序列），按 E2E 报告的场景脚本逐个重放：快速通道 DONE / 修复回路 DONE_FLAGGED / NEED_REPLAN 重规划 / 审计不通过→协商通过 / 预算耗尽中止。断言：终态、里程碑序列、events.jsonl 轨迹（依赖 G7）、预算数值。
- **验收**：≥10 个场景用例进 `vitest run`，CI 全绿；`docs/E2E测试报告` 更新「已固化为自动化用例」标注；这是 1.0 的前置条件。

### G16 性能回归护栏（轻量）
- **现状**：快照节流已有「20 save ≤ 2 write」单测；无「单 turn 同步 IO」整链断言。
- **方案**：批次 D 的 E2E 场景里加一条：完整任务周期内 SnapshotStore 实际写盘次数 ≤ 迁移次数/2 + 终态数（防未来把同步写加回热路径）。
- **验收**：用例随 G15 落地。

## 5. 批次 E — 版本策略

### G17 1.0.0 出口判据（semver 承诺生效）
- **判据（全部满足才打 1.0.0）**：
  1. G1（覆盖率 ≥80% 门禁）、G2（lint 零 error）、G4（3 版本矩阵）全绿；
  2. G6（快照版本化 + 迁移函数表就位）、G7（事件流）、G12（CONFIG.md 全键）、G15（E2E 固化 ≥10 场景）完成；
  3. release workflow（G10）跑通一次 tag dry-run；
  4. 4 轮方案的全部 P0/P1 遗留清零（当前仅剩 E2E 一项）。
- **1.0 后承诺**：配置键只增不改语义（弃用先 warn 一个 minor 周期）；快照版本升级必须带迁移函数；FSM 迁移语义变更必须过 ci-checks 不变量 + E2E 场景更新。

### G18 版本号与命名
- 本方案批次落地期间版本 0.5.x（每批一个 minor），全部完成打 **1.0.0**。CHANGELOG 按「批次 = minor」记录。

## 7. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| biome 一次性 format 造成大 diff | format 单独提交；lint 规则先 warn 后逐步 error |
| exactOptionalPropertyTypes 修复波及面 | 独立提交、不改运行时行为，151 用例回归背书 |
| events.jsonl 增大磁盘占用 | 5MB 滚动 + `events.enabled` 开关；快照仍是权威态 |
| mock 网关 E2E 与真实宿主行为偏差 | 场景直接取自已验收的 E2E 报告；报告注明差异面（真实子代理时序）由宿主回归覆盖 |
| release workflow 凭据 | NPM_TOKEN 用 GitHub secret；workflow 权限保持 least-privilege（contents: read + id-token: write for provenance） |

## 8. 明确不做（记录理由）

- **会话级并行**：ADR #19 串行是产品语义，并行化涉及熔断/预算隔离重设计，无需求信号，不属于「工业级缺口」；
- **i18n**：用户面全中文是产品决策；
- **js-tiktoken 精确计数**：CJK 混合估算（v4）误差已满足预算护栏用途，引入 10MB+ 依赖得不偿失；
- **数据库替换 budget.json**：单文件 + 原子写 + 保留窗已满足单宿主运维。
